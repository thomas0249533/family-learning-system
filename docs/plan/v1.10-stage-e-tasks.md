## 任务 E1-a · FSRS 时间口径审计与纯函数准备（前端/数据层 · 低风险 · 立即开工）

**范围**：`src/core/review/fsrs.ts`、`src/core/review/reviewScheduler.ts`、相关日期工具。

**要求**：
1. 暂不修改任何业务逻辑。
2. 审计所有 `toISOString()` 序列化/切分日期的点，输出清单（文件:行号 + 口径 + 偏差）。**已确认的写入口**（审计起点，不是终点）：
   - `fsrs.ts:88` `due: card.due.toISOString()`
   - `fsrs.ts:97` `last_review: card.last_review ? card.last_review.toISOString() : null`
   - `reviewScheduler.ts:63` `legacyCardFromStage` 的 `due`
   - `reviewScheduler.ts:126` `scheduleReview` 的 `lastReviewAt`
3. **审计重点是消费端**：谁按字符串前缀/切片（`.slice(0,10)`、`split('T')[0]`）比日期——那才是时区偏差的直接受害者。
4. 纯函数：`localDayKey` **已存在**于 `src/core/motivation/streak.ts:120`（`dailyStats.ts` 已在复用，注释明写「勿用 UTC/toISOString」）。**不要新造重复函数**；决定是直接 import（评估 core/review → core/motivation 反向依赖是否可接受）还是提取到中立模块让 streak.ts re-export。给理由。
5. 单测覆盖东八区 **20:00 / 23:59 / 00:01** 三个边界 + 跨月 + 跨年。

**验收**：单测全绿；不引起任何已有测试变红；`npx vue-tsc --noEmit -p tsconfig.json` 干净。

**已知坑**：
- 测试不能假定进程 TZ 是 +08:00：用带偏移的 ISO 串构造 Date，断言写成「该偏移下的期望」，注释写明理由。
- 若审计发现「UTC 点比上面列的多」或「有比 fsrs.ts 更严重的消费端」，如实报告，不许顺着本清单的假设写。

## 任务 E1-b · FSRS 数据迁移与写入口更新（高风险 · 主程亲自把关）

**范围**：`src/core/review/`、`src/core/storage/`（迁移）、`src/db/index.ts`（版本号）。

**要求**：
1. **先写迁移测试再动写入口**：造旧 UTC 数据 → 走迁移 → 断言本地口径正确、无重复无遗漏、复习队列不多不少一条。没有迁移测试不许改写入口。
2. 迁移方案由 E1-a 审计结论决定，两个候选（不许拍脑袋）：
   - **A. 日粒度字段改存 `YYYY-MM-DD` 本地日键** → 旧行必须迁移；
   - **B. 时刻字段改存带时区 ISO（`+08:00`）** → `new Date()` 能同时解析 `Z` 与 `+08:00` 两种串，旧行**可能无需重写**，只需保证所有读取端走 `new Date()` 解析、不按字符串切片，且混合格式可解析。
3. **DB 已到 v4**（`src/db/index.ts:141`，v4 = `migrateProfileV4` 补 profileId）。新迁移是 **v5**，遵守 `migrateV4.ts` 文件头四条铁律：只用 `tx.table(...)`；纯计算与哑 IO 分离；失败不 rethrow；版本号推进后 `upgrade()` 不再触发 → 补偿靠 recovery 文件（照 `migrateV4Recovery.ts` 建）。

**验收**：完整 `npm run verify` + 全量 e2e。
**反向验证**：把写入口改回 UTC → 迁移测试必须红。贴红绿原文。

## 任务 E2 · 智能错题重组引擎（算法层 · 不动 UI）

**范围**：`src/core/mistake/`（现有 `mistakeCause.ts` / `mistakeRules.ts`）、`src/core/progress/`（`ownerIndex.ts` / `progressRecord.ts`）、`src/core/stores/userData.ts:215`（`recordProgress` 写入口）。

**要求**：
1. **第一步必须先写测试**：证明临时包的进度正确归属到**原 KP 所属包**（V1.3 口径：`recordProgress` 第 1 参数 = 入口包，落库 `packageId` 由归属解析决定），且不污染包计数成就（`ctx.packages`，见 `src/core/motivation/achievementMeta.ts` 与 `AppShell.vue` 的 distinctPackages）。
2. 生成 `special-weakpoints-auto` 包，遵守铁律：`manifest.examMode: true` + `manifest.sourceUnitIds` 必须同时写；`manifest.dependencies` 必须为空（非空会被当聚合包）。
3. 包 id 稳定，每次生成**覆盖**旧包，不累积；包是设备级资产、不进备份（裁决 1），重建策略 = 按需重新生成。
4. 选题规则：错因 `knowledge` 或连续失败 ≥2 次优先；`careless` 少量混入（全混 careless 会让孩子练「粗心」而不是练不会的）。
5. **不得改动任何 UI 组件**（UI 是 E3 的事）。

**验收**：单测证明归属逻辑与成就不污染；全量测试不红。
**反向验证**：把归属临时改成「落到临时包自己」→ 归属测试必须红。

**范围**：`src/views/Mistakes.vue`、`src/views/Parent.vue`、`src/core/report/`（`reportGenerator.ts` / `canvasKit.ts` 已存在）。
