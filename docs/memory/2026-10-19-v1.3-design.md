# 2026-10-19 · V1.3（成就 P0 + 工程债 E-01~E-03）设计阶段

## 一、关键事实更正：`knowledgePointId` 在运行时是**唯一**的

**这是本轮最重要的认知纠正，后续所有涉及 kpId 的讨论都必须建立在这个前提上。**

- `content/**/*.json`（构建中间产物，**裸 JSON 单文件导入路径**）里 kpId 是**短 id 无前缀** → 存在同名不同义：`unit-english-7-up-rjb-p1`~`p7` 各自定义一套 `kp-reading-001`/`kp-word-001`/`kp-sentence-001`/`kp-grammar-001`/`kp-grammar-002`/`kp-phonetic-001`/`kp-writing-001`（各指不同知识点，title 各异），共 49 个知识点共用 7 个 id；`kp-reading-001` 还被 `special-chinese-4-up-reading` 用作「梅雨潭」（跨学科）。
- **用户实际导入的 zip（`.lpkgset.zip`）里 kpId 带包前缀**（如 `unit-english-7-up-rjb-p1::kp-reading-001`）。实测：43 个包 / **472 个 kpId，每个只被 1 个包声明，零重复、零跨学科冲突**。

⇒ 结论：**「同一知识点只保留一条」的真正目标是 `(归属包, kpId)`，而不是 `kpId`**；但「按裸 kpId 去重会塌 49→7」只作为**裸 JSON 路径的边界保护**保留，**不能当作主路径反例**。

⚠️ **踩坑教训**：第一轮调研扫 `content/**/*.json` 就下了结论，属于**取样错误**（看了构建中间产物而非运行时产物）。以后凡涉及「id 唯一性 / 数据规模」的判断，必须以 zip 或 IndexedDB 真实数据为准。

## 二、归属包判据：必须用 `knowledgePoints` 声明，不能用 `units` 引用

实测覆盖率（898 个 `(入口包, kpId)` 组合，严格规则 `|own|==1` 才归一化）：

| `own` 定义 | 归一化成功 | 多候选歧义 | 零候选 | 跨学科 |
|---|---|---|---|---|
| 包 `units` 里**引用了**该 kpId | 446（**49.7%**） | 452 | 0 | 0 |
| 包 `knowledgePoints` 里**声明了**该 kpId | 898（**100%**） | 0 | 0 | 0 |

**原因**：`term` / `sprint` / `special` / `daily` 包的 `units` 是**聚合视图**（从 unit 包拼来），同一 kpId 在其 units 里也会出现 → 3–5 个候选 → 大量误判"歧义"。按入口类型看 units 口径：unit 入口 144 组合仅 37 成功（**26%**）、sprint 63 组仅 2 成功、daily 15 组 0 成功。

**只有 `knowledgePoints` 是所有权声明**。代码里已有同语义实现：**`TopicDetail.vue:399-407` 的 `ownerPackageIdOf`** 扫的就是 `pkg.knowledgePoints` —— 提取为纯函数复用（纯内存、O(包数×KP数)、不入 DB、启动时建一次 `Map<kpId, pkgId>` 索引，**不放热路径**）。

**最终规则（严格三分支，不引入 tie-break）**：
```
own = 所有「knowledgePoints 里声明了该 kpId」的包
|own| == 0 → null（保留原记录不动）
|own| >= 2 → null（歧义即不动；现在只对裸 JSON 导入路径生效）
|own| == 1 → 该包即归属包
另：归属包 subject ≠ 入口包 subject → null
```
**写入端必须最严**（错了永久污染 progress、用户无感知、不可重算）；**统计端可宽松**（`computeMasterySummary` 内部允许「同 kpId 且 title 全同」合并计 1，纯函数可重算）。风险与收益不对称，不能用同一套宽严。

## 四、掌握率三处口径统一（`docs/mastery-metric-definition.md`，255 行）

三处**根本不是同一个指标**：分子全是「progress 记录条数」（三处都不去重），分母三种口径：

| 处 | 位置 | 分子 | 分母 | 去重键 |
|---|---|---|---|---|
| Home | `Home.vue:283-292` | `filter(status==='已掌握').length` | `Σ pkg.knowledgePoints.length` | 无 |
| Parent | `Parent.vue:183-212` 总览 / `215-245` 学科 | 同上 | `Σ` 每学科 KP 条数（学科归属用**裸 kpId 反查**，后者覆盖前者） | 无 |
| Report | `reportGenerator.ts:50-160` | 同上 | `Set(裸 kp.id).size` | **裸 kpId** |

`>100%` 四个成因：① 分子不去重 + 分母口径不一致；② 孤儿记录（包已删、progress 残留）→ 分子算分母不算；③ **Report 分母被裸 kpId 去重缩小 → rate 被抬高**（最严重）；④ `Home.vue:414` 的 `Math.max(total-mastered-learning, 0)` 只兜住饼图负值，`Home.vue:158` 的 `chart-rate` 仍直接显示可 >100 的 `masteryRate`。

补充事实：**Parent 的 `stats` 没有 rate 字段**，掌握率只在 `subjectStats`（学科行）→ 实际是 **3 处 4 个数值面**（Home 总率 + Parent 学科率 + Report 总率 + Report 学科分布）。

**统一签名（两入参，单入参算不出分母）**：
```ts
computeMasterySummary(packages: LearningPackageRecord[], progress: ProgressRecord[]): MasterySummary
// { total, mastered, learning, needReview, unlearned, notStarted, rate, orphanRecordCount }
```
`orphanRecordCount` 为**诊断桶**（不进任何桶）。三处全部调用它，禁止就地重写公式。
硬约束：`mastered <= total`、`rate <= 100`、`notStarted >= 0`。
行为变更（QA 需基线）：**Report 整体掌握率会显著下降**（分母正确展开，不是退步）；Home 略降或持平且不再 >100；Parent 学科率学科间重新分配。
