# 2026-11-04 · V3.1.2 发版：今日任务 KP 取题修复 + 在线更新 E009 + 剑桥英语选项打散

## 背景：用户报「今日学习任务，词语题全是奇观」

四上语文「词汇默写」把 30–50 个词放进**同一个 topic**，每个词是独立 KP、各只有 1 道默写题。
今日队列列表写「柔和 / 堵车 / 顿时」，点进去每一项却都是「奇观」。

### 根因（应用代码 bug，非内容数据问题）

1. `dailyPlanService.buildIndex` 把每个 KP 映射到**整个 topic**（`idx.kp` 的 entry 带 topicId +
   `exercises`，词汇 KP 的 availableQuestions = 1）；`DailyPlanItem` 因此带
   `knowledgePointId`（如「柔和」=`kp-cn4-u1-w15`）。
2. `TodayPlan.startItem` 跳转只带 `mode=session` / `session` / `limit`，**没带 KP**。
3. `TopicDetail` 队列模式从 `allTopicExercises`（整个 topic 的题池）用
   `selectSessionQuestions(all, frozenLevel, limit)` 挑题；词汇题全是「基础」档，
   同档保持题库原顺序 → **永远命中该 topic 第一题「奇观」**。
4. 连带 bug：`computeSessionLevel()` 取 `topicKpIds[0]`（也是「奇观」）算难度，
   等于拿别的词的作答记录决定本项难度。

影响面：`review / mistake / weak` 三类项，凡「一个 topic 含多个 KP」均错配；`new` 项按单元
新学、无 KP，本来就该做整个主题，不受影响。

### 修复（commit `4211c76`）

- `src/core/plan/adaptive.ts` 新增纯函数 `filterByKnowledgePoint(pool, kpId)`：
  ① 原值精确匹配优先（避免短 id 串包）→ ② 去 `pkg::` 前缀兜底（限定 id ↔ 裸 id 混用）
  → ③ 筛不到退回全池（**不空转红线**：点进队列项出现空题单比给错题更糟）。
  泛型不加约束，避免把元素类型收窄成只有 `knowledgePointIds`、丢掉 `metadata`
  （否则 `selectSessionQuestions` 接不住，typecheck 会报 `unknown[]`）。
- `TodayPlan.startItem` 通过 `?kp=` 把队列项知识点带进会话。
- `TopicDetail`：队列模式**先按 KP 筛、再按难度挑**；`sessionLimit<=0` 分支也要筛（老链接）；
  `computeSessionLevel` 改用 `sessionKpId`；`allTopicExercises` 显式标注 `computed<any[]>`。
- 测试：`tests/adaptive.test.ts` 新增 9 条，含「柔和项 + limit=1 必须拿到柔和而非奇观」
  与「不筛必然命中奇观」的成因锁定。

### 顺带修掉的门禁失败

`tests/movers-pack.test.ts` 的 `EXPECTED` 表把官方 Answer Key 的**字母 'A'** 写死了，
而上一轮剑桥英语选项打散后字母已变（正确内容未变）。改为按「answer 指向的选项文本」
比对官方答案文本，并新增「单选答案位置已打散（任一字母占比 < 50%）」断言，
防「无脑选 A」回潮。**教训：内容修复若改变了测试中被引用的"稳定事实"，测试也要同步换锚点。**

## ⚠️ 重要事实纠正：定时任务「推送成功」是误判

用户报「定时任务已经成功了、英语版推送成功了、可以删任务了」，但 git 实测：

- 远端 `main` 一直停在 `2fda2ec`（英语四上词汇重建），**本地累计 59 个提交从未推上去**；
- 定时重试自动化已自停删除（再删时返回 already deleted），但它显然没有真正完成推送，
  或者用户把「早前 2fda2ec 那次内容推送」误认成本轮成功；
- 结果是：家庭端点「检查题库更新」时，E009 报错（应用代码 bug）、词语题错配（应用代码 bug）
  都收不到修复 —— 这也是用户问「发版成功了吗？没检测到更新」的直接原因；
- 本次靠 `push-to-github.mjs`（tree API 以远端为父重建 commit）一次性同步全部内容后才真正落地。

**教训：自动化报「成功」不等于远端状态已变。发版前必须 `git fetch` 后核对
`git rev-list --count origin/main..HEAD` 与远端 `releases/latest/download/latest.json` 的 version，
两项都对了才算发完。**
