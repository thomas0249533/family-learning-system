# 2026-11-04 · V3.1.3：数据丢失事故复盘与「清空前恢复点」

## 事故（真机，用户口述 + 截图）

用户在 3.1.1 时期清空过学习包，学习进度丢失；之后升级了系统、更新了学习包，
到 3.1.2 才想找回。截图显示「🛟 自动快照」里**只剩 2026-11-04 21:52 一份**，
且是清空**之后**拍的空数据。结论：进度找不回来了。

顺带纠正：用户找 `AppData` 时停在 `C:\Windows` 目录没找到。`AppData` 是隐藏目录，
实际路径是 `%LOCALAPPDATA%\com.family.learning\EBWebView\Default\IndexedDB\...leveldb`。
但即使找到也没用 —— Dexie 的 `clear()` 写入墓碑，旧记录在 LevelDB 压缩前理论上残留，
取证级恢复成功率极低，不值得让家长折腾。

排查时在本机（开发机）确实找到了该 leveldb 目录，但最后写入停在 **2026-10-29**，
里面残留的是学习包题目 JSON（`knowledgePointId` 是题目字段），不是进度记录；
今天升级 3.1.2 的写入不在这台机器上 —— 孩子做题用的是另一台「家庭端」电脑，
所以任何恢复动作都必须在那台机器上做。**这条要记住：开发机 ≠ 家庭端。**

## 根因（三个缺陷叠加，任一存在都不至于彻底丢）

1. **清空前不拍快照**：三个危险按钮直接删数据，没有留回滚点。
2. **清空把快照一起删了**：`clearAllData()` 执行 `db.settings.clear()`，
   而每日自动快照就存在 `db.settings` 的 `backup:snapshots` 键里 ——
   最危险的那个按钮，把唯一能救命的东西一起抹掉了。
3. **7 份滚动窗口**：清空后每天首次启动拍一份空数据新快照，
   7 天后清空前的每日快照被挤掉，最后一个恢复入口消失。

## 修复（commit `b33e83c`，最小侵入）

**不动 db schema、不新增 settings 键**（因此 `GLOBAL_KEYS` /
`EXPORT_EXCLUDED_GLOBAL_KEYS` / `GLOBAL_NEVER_MERGE` 都不用改，静态扫描零问题）：

- `SnapshotEntry` 加 `id` / `kind: 'daily' | 'preClear'` / `reason`；
  `normalize()` 把 3.1.2 及更早的无 id/kind 条目兼容为 daily。
- `capturePreClearSnapshot(reason)`：**强制拍**（不受"今天已拍过"限制，
  一天连点两次清空各留一份），失败返回 `ok:false`。
- `withPreClearSnapshot(reason, action)`：**拍不上就不许动数据**。
  最后一道保险不能像每日快照那样静默失败，宁可清空失败也不能裸奔。
- `clearAllUserDataExceptSnapshots()`：清 4 张业务表后把快照**写回**，
  替换 `Settings.vue` 里原来的 `db.settings.clear()`。
- `prune()` 按类别分开计数：daily 保留 7 份，preClear 单独保留 10 份，互不挤压。
- `restoreSnapshotById(id)`：同一天可有多份保护快照，date 会重复，必须用 id 定位；
  保留 `restoreSnapshot(date)` 给老调用方，标 deprecated。
- `clearSnapshots()` 只清 daily；保护快照要逐条二次确认才能删（`deleteSnapshot`）。
- `AutoSnapshotPanel` 置顶展示「🛟 清空前恢复点」（原因 / 时间 / 应用版本，警示色）。
- 三个危险按钮的确认弹窗写明"执行前会自动保存一份恢复点"，成功后 Toast 也提示。
- `fakeDexie` 补 `Table.clear()`（真 Dexie 有，测试基础设施缺口）。

## 回归测试（`tests/pre-clear-snapshot.test.ts`，10 项）

钉死五条不变量：① 清空前必拍且带原因、含完整进度；② **拍失败中止清空，
进度原封不动**；③ 清空所有数据后快照仍在且能真的把进度合并回来（端到端闭环）；
④ 连续拍满 7 份 daily 也挤不掉 preClear；⑤ 清空每日快照不误删保护快照。
另覆盖同一天连拍两份 id 不同、旧条目兼容、保留上限。

`verify` 全绿：124 文件 / 4120 项。
门禁两处被有意触发并据实更新：`check:profile-scope`（`clear()` 跨档案，
加带理由豁免）、`settings-keys` 访问点计数 60 → 67（新增 7 个访问点全落在
已登记的 `backup:snapshots` 键，未引入新键）。

## 给用户的说明（重要）

- **3.1.3 找不回这次已经丢的数据**：事故发生在旧版本，旧代码没留恢复点。
  本版只保证以后任何清空都能回滚。
- 装 3.1.3 后建议立刻做一次「📤 导出 → 家庭备份」把文件存到电脑，
  这是唯一能扛住「整个 AppData 被删 / 重装系统」的保险；快照仍在同一数据库里。
- 恢复是**合并**语义（较新者胜）：清空后新做的题不会被旧恢复点覆盖。

## 设计取舍

- 没选「快照挪到独立 Dexie 表」：要改 db v9、fakeDexie 7 张表、迁移逻辑，
  事故刚发生，稳定性优先；共用已登记且已排除导出的键，改动最小、回归面最窄。
- 没选「清空时自动下载备份文件」：Tauri 侧没有 fs 插件，弹下载框会打断操作，
  且家长未必保存；改为在弹窗里**提示**手动导出。
