## 0. 为什么 Stage A 是这些事

当前系统最大的风险不是“功能少”，而是 **数据看起来在、实际已经错了却不报错**。V1.4 已经踩过两次同类问题：

- `progressMerge` 分组键漏 `profileId` → 两个档案学同一课时，B 的 upsert 把 A 的行改写，行数不变、零报错。
- `DataCloneError`：Vue 深层 `ref` 代理写进 IndexedDB 才炸，单测测不到。

**Stage A 的目标**：把“静默串数据 / 静默丢数据”的窗口全部堵上，并用反向验证证明防线会红。学习闭环（Stage C）必须建立在数据可信之上，否则推荐和归因都是错的。

### A1 · 跳版迁移推演测试（P0，最高优先）

#### 问题

Dexie 从 v1 直接升 v4 时，会按顺序跑 v3、v4 的 `upgrade()`。v3 钩子“永不 rethrow”，失败只写标记；v4 会继续给“尚未归一化”的行补 `profileId`；然后启动补偿再跑 v3 recovery。这个时序没有逐行推演过，而它是“用户从老版本直接装最新版”的最常见路径。

#### 做法

| 步骤 | 内容 |
|---|---|
| 1 | 新增 `tests/migrate-jump-path.test.ts`，用假 `tx`（只需 `table() → toArray/put/update/delete/bulkDelete`）构造库状态 |
| 2 | 覆盖三条路径 × 三种 v3 结局：<br>① v1→v4（v3 成功）<br>② v1→v4（v3 计划失败写 `failed`，v4 照跑，启动补偿补 v3）<br>③ v2→v4（v3 成功/失败）<br>④ v3→v4（直接升） |
| 3 | 每条路径断言：<br>• `progress/mistakes/examSessions` 所有行 `profileId` 非空且等于 `'default'`<br>• 可唯一归属的行 `packageId` 已归一化，歧义行原样保留<br>• `Σ correctCount / Σ wrongCount / Σ studySeconds` 前后严格相等<br>• `settings` 旧键保留、新分片键齐全（9 个 per-profile 键）<br>• `achievements` 解锁 id 集合前后完全相同（迁移不碰 settings 的成就语义）<br>• **V1.5 重复字段原样过迁移**：`achievements` 值用 V1.5 形状（`repeatCount` / `lastRepeatPeriod` / grow 游标 `repeatBase`），迁移后逐个相等 —— v1/v2 没有这些字段，但打过 V1.5 补丁的库有；游标被改一个字节，下一次结算就按错误基线算增量<br>• 第二次跑 plan 为零（幂等） |
| 4 | 反向验证：把 v4 apply 顺序改成“先 delete 后 put”，A1 应红；还原后绿 |

#### 源文件

- `tests/migrate-jump-path.test.ts`（新）
- `src/core/storage/migrateV3.ts` / `migrateV4.ts`（只读不改）

#### 验收

- 三条路径 × 三种结局全绿
- 反向验证记录在 commit message
- 单测新增 ≥ 18 条
- V1.5 repeat 三字段（`repeatCount` / `lastRepeatPeriod` / `repeatBase`）原样过迁移的断言随执行回填（2026-10-21 对齐增补）

### A2 · 假 Dexie 替身审计 + 档案隔离单测（P0）

#### 问题

V1.3 草稿要求“未知索引名直接 throw”，但 V1.4 文件清单没列 `tests/user-data-store.test.ts` 的修改。如果假 Dexie 不认新索引，测试会静默 fallback 到 `rows.find(...)` 返回 `undefined`，测试“通过”，生产却抛错。

#### 做法

| 步骤 | 内容 |
|---|---|
| 1 | 审计 `tests/helpers/fakeDexie.ts`（或等价文件）：每张表声明 **v4 真实索引清单**；`where()` 遇到未知索引名 **throw**，禁止 fallback |
| 2 | `settings` 键默认补 `:default` 分片，或测试显式传 pid；禁止“忘了分片也能读到” |
| 3 | 跑全量单测，修因索引名/分片导致的红（预期一批，按真实语义修，不放松断言） |
| 4 | 新增 `tests/user-data-store-profile.test.ts`：<br>• 档案 A、B 各写同一 `(packageId, kpId)` → 两行，互不覆盖<br>• 档案 A 写、B 读 → B 读不到<br>• 同一档案重复写 → 只 1 行、计数累加 |
| 5 | 反向验证：把 `where` 的未知索引改回静默 fallback，A2 的隔离用例应红 |
| 6 | **类型盲区纪律（硬性）**：`tsconfig.json` 只 include `src/`，`vue-tsc` 查不出 `tests/` 里的类型错误 —— V1.5 repeat 改动已踩过（测试夹具少写字段，直到运行期才掉错分支）。本阶段改公共类型（`MistakeRecord` / `ResolvedUnit` / `MergePlan` 等）时，**必须手动 `grep -rn "字段名" tests/`，确认所有夹具补齐新增字段**，核查记录写进 commit message。（长期解法：Stage B 评估把 `tests/` 纳入 tsconfig 或开启 Vitest typecheck 模式，Stage A 不做） |

#### 验收

- 假 Dexie 未知索引抛错
- 全量单测绿
- 新增 ≥ 6 条
- 反向验证记录
- 公共类型改动均做过 `grep -rn "字段名" tests/` 核查

> **执行记录（2026-10-21，A2 收尾 + A6 前置补牙）**：抽取后全量单测**全绿**，按"全绿 = 替身静默 fallback"的怀疑审计，补了六道牙：复合索引 `.equals()` 必须传满元数的数组（少传 `profileId` 必须炸）、单列索引拒收数组、`equals(null/undefined)` 抛错、`add()` 撞主键抛错、v4 形态下三张表每行必须带非空 `profileId`（老数据夹具 `requireProfileId:false` 显式豁免）、读接口交副本。新增 `tests/fakeDexie-guard.test.ts`（20 条，含索引清单与 `src/db/index.ts` 原文逐字比对）。四个生产代码变异（少传 profileId / pid 写死 / 索引名打错 / 行缺 profileId）**各自独立**跑全量均被抓（5/2/4/11 条红）。`migrate-jump-path.test.ts` 的内联假库同期收编 —— "单一真相"自此名副其实。

### A4 · `addMistake` 归属包收口（P0）

#### 问题

`addMistake` 直接把入口包写进 `db.mistakes`，而 `Mistakes` / `Review` 用 `mistakes.packageId` 做学科标签与包标题。一道题跨 2 个 KP、分属不同包时，取 `kpIds[0]` 的归属包是“猜”的。

#### 做法

| 步骤 | 内容 |
|---|---|
| 1 | 在 `src/core/progress/progressIdentity.ts` 新增 `resolveMistakeTarget(kpIds, entryPackageId, index)`：规则与 `resolveProgressTarget` 一致——唯一归属才归一化，歧义/零候选保留入口包，subject 闸门 |
| 2 | `userData.addMistake` 内部调用该函数解析 `packageId`；调用方签名不变（第 1 参数语义仍是入口包） |
| 3 | 错题卡显示归属包标题（若 `packages` 里能找到），找不到显示入口包，不显示裸 id。**只显示 `title`；包名过长单行截断加 `...`** —— 呼应 V1.5"组件极简，不引入多余配置"的产品思路（不给家长单配 step，就不给卡片配折叠/展开/多行） |
| 4 | 新增 `tests/mistake-owner.test.ts`：<br>• 单 KP 唯一归属 → 归属包<br>• 两 KP 分属两包 → 取第一个 KP 的归属包（与现状一致，不扩大改动）<br>• 零候选 → 入口包<br>• 跨学科 → 入口包 |
| 5 | 反向验证：把 `addMistake` 改回直接写入参包，A4 应红 |
| 6 | **类型盲区纪律（同 A2）**：`resolveMistakeTarget` 及涉及的 `MistakeRecord` 等公共类型如有调整，必须 `grep -rn "字段名" tests/` 核查夹具补齐 |

#### 验收

- 新增 ≥ 5 条
- Mistakes 页人工核对一条跨包错题显示归属包

### A6 · 导入并发窗口的“执行前快照校验”（P1，Stage A 内可降级）

#### 问题

`planMerge` 在事务外读快照，执行时本机可能已被写（孩子边导入边答题）。极端情况下，一条新学习记录会被较旧快照覆盖。

#### 做法（两级，优先第一级）

| 级别 | 内容 | 成本 |
|---|---|---|
| **L1（必做）** | 导入预览页与执行页显示固定提示：“导入期间请不要在学习页答题；若刚答过题，请返回首页后再导入。” 并在执行按钮上做 2 秒防连点 | 0.5 天 |
| **L2（选做，若时间允许）** | `applyMergePlan` 事务内、写入前，重新读一次 `progress/mistakes` 的关键行（按 plan 里涉及的 key），与 plan 基于的快照比对；不一致则中止事务并提示“检测到新的学习记录，请重新预览后导入” | 1–1.5 天 |

#### 验收

- L1 文案落地
- L2 若做，新增单测模拟“plan 后、apply 前插入一行” → 事务中止、库无变化
- 反向验证：去掉校验应红

> 若 Stage A 时间紧，L2 可延到 Stage B，但 L1 必须做，且文档里把“影响面极小”替换为具体窗口描述。
