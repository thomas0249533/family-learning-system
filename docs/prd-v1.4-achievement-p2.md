## 0. 本轮裁决（4 条，先读这个）

| # | 问题 | 用户裁决 | 对本文的影响 |
|---|---|---|---|
| D1 | 家庭墙是否跨设备 | **要跨设备**，方式是**备份导出 + 导入**，且**导入不得影响已有家庭墙进度** | P0-3 整节重写；备份格式升 `formatVersion: 2`；新增「跨设备导入」批次 B2 |
| D2 | 自定义成就要不要支持条件表达式 | **V1.4 只做 `manual-check` + `counter`**，表达式留 V1.5 且必须配沙箱 | P0-1 白名单收紧并写入「不可扩展」声明 |
| D3 | 档案上限 | **4 个** | P0-2 硬约束；导入时不得突破 |
| D4 | 打印分页 | **按小组分页** | P1 排版规则重写；AC-P2-10 判定改写 |

其中 D1 是破坏性最大的一条：**"跨设备"不等于"云同步"**。本文所有跨设备能力都建立在"用户自己把备份文件从 A 搬到 B"之上，不新增任何网络请求、账号体系或服务端组件（见 §2 非目标）。

## 1. 背景与问题

V1.3 把成就系统做成了「确定性收集」：28 枚写死在代码里、单孩子、数据只在本机。
现在四件事开始卡住产品：

1. **内容不能扩**：想加一枚成就必须发版改代码。家长想加一条"本周读完一本课外书"这类自家规则，只能等我们。
2. **家庭场景缺位**：俩孩子共用一个数据库，"他拿了 10 枚、我 3 枚"这种对比迟早发生 —— 但现在无法区分是谁的。
3. **家长无法留存/打印**：家长想把孩子的徽章打印出来贴墙上，或导出成一张图发家族群，现在只能截图。
4. **跨设备就断**：孩子在书房的电脑上学、在客厅的平板上复习，两台设备的成就各算各的；把备份搬到另一台后，
   现有 `importUserData` 的 merge 模式会**用备份整键覆盖 `settings`**（`db.settings.put`），
   导致目标设备原有的成就墙被抹掉。这不是"少同步一次"，是**丢数据**。

第 4 条是这一版必须解决的硬问题，也是 D1 裁决的直接来源。

## 2. 目标 / 非目标

**目标**
- G1 成就定义可外部化：JSON 包能被校验、预览、启用、回滚，且**不破坏 28 枚内置成就**。
- G2 家庭内可见：家庭成员能看到彼此的成就墙，**没有排行**；且**数据可跨设备搬运**（备份文件为本，不做实时同步）。
- G3 多孩子隔离：每个孩子独立的进度/错题/成就/打卡，互不污染，上限 4 个档案。
- G4 可带走：成就数据可导出为结构化文件、可重新导入（**导入只增不减**）、可打印成按小组分页的页面。

**非目标（明确不做）**
- ❌ 任何形式的排行、名次、"超过 xx% 的人"。
- ❌ 用成就兑换实物/特权/题库（触碰不变量第 1 条"不可购买"）。
- ❌ **云端账号体系、实时同步、家庭组网**。跨设备只走"导出文件 → 人工搬运 → 导入合并"这一条路
  （D1 裁决）。不新增任何网络请求、服务端组件或第三方 SDK。
- ❌ 给儿童展示任何概率数字（发现机制已在 V1.3 落地，仍不展示概率）。
- ❌ 成就"消失/回收"（已解锁只增不删，V1.3 既有语义）。**跨设备导入同样遵守这条**：导入永远不删本机记录。
- ❌ **`rule.kind` 的条件表达式 / 脚本**（D2 裁决）。V1.4 白名单只有 `manual-check` 与 `counter`。

## 4. 需求池

### P0-1 · JSON 成就包

**形态**：与学习包同构的 zip/目录，`manifest` + `achievements.json`。

```jsonc
// achievements.json（草案）
{
  "schemaVersion": 1,
  "packId": "custom-family-2026",
  "achievements": [
    {
      "id": "custom::reading-charlotte",     // 必须带 `custom::` 前缀，避免与内置 28 枚撞 id
      "icon": "📖",
      "title": "读完一本课外书",
      "desc": "把一本书从头读到尾，并说出主角的一个变化。",
      "category": "E",                        // 复用 M/G/B/E 四类
      "source": "core",                       // core|subject|habit|hidden
      "tier": "common",                       // 或交给我们按规则推导
      "metered": true,
      "target": 1,
      "rule": { "kind": "manual-check", "prompt": "家长确认" }  // 白名单：manual-check | counter（D2）
    }
  ]
}
```

**关键约束**
- **可判定的规则才允许进包**（D2 裁决）：V1.4 白名单**只有两种**——
  - `manual-check`：家长手动勾选（`prompt` 为勾选时的确认文案）；
  - `counter`：复用现有 progress 聚合字段，形如 `{ "kind": "counter", "metric": "masteredKp", "target": 10 }`，
    `metric` 必须在**枚举白名单**内（`masteredKp` / `totalAttempts` / `studyDays` / `streak`），
    **不允许**写任意路径、任意表达式、任意脚本。
- **条件表达式明确留到 V1.5，且必须配沙箱**。这是 D2 的原话裁决。V1.4 的 schema 里**不预留 `expr` 字段**——
  预留一个永远报错的字段只会让家长写出无效配置；等 V1.5 用一个真正的 `schemaVersion: 2` 加。
  校验器遇到未知 `rule.kind` 一律按"不支持"拒绝（AC-P2-2）。
- `id` 必须 `custom::` 前缀。导入时若与已有自定义包同 id：**冲突即拒**，不静默覆盖。
- 内置 28 枚**不可被覆盖**（即使包内写了同 id，也直接拒绝并报错）。

**功能**
1. **校验**（`validate:achievements`）：schema + 语义（id 前缀、category/source/tier 合法、
   `target ≥ 1`、`metered=false` 时不得带 `target`、文案长度上限、图标必须是单个 emoji）。
2. **预览**：不落库，只算"若启用会新增哪些卡、与现有卡是否重名/重 id"，给一张 diff 表。
3. **启用 / 停用**：停用即从视图移除，但**已解锁记录保留**（重新启用后仍在）。
4. **回滚**：保留上一版包的快照，一键回滚；回滚**不动**解锁记录。
5. **审计**：每次启用/停用/回滚写一条 `achievement:audit` 记录（时间、动作、packId、影响枚数）。

### P0-2 · 多孩子档案（`profileId` 隔离）

**这是本文件里唯一的「数据模型变更」，也是唯一需要 `version(4)` 的项。**

| 项 | 现状 | 变更 |
|---|---|---|
| `progress` | 主键 `id`，语义键 `(packageId, kpId)` | 加 `profileId`（索引 `[profileId+packageId+knowledgePointId]`） |
| `mistakes` | 同上 | 加 `profileId` |
| `achievements`（settings） | 单个键存 `UnlockedRecord[]` | **拆成前缀键** `achievements:<profileId>`（每档案一个键） |
| `settings` 中的打卡/每日统计 | 单份 | 同上，键加 profile 前缀 |
| 导出格式 | `payload` 无 profile 概念 | `formatVersion: 2`，含 `profiles[]`；**仍能读 v1**（读入后落到 `default` 档案） |

为什么是**前缀键**而不是"一个 `Record<profileId, UnlockedRecord[]>` 大对象"：
大对象每次解锁都要**整块重写**，两个页面同时写入时后写的那份会覆盖前一份（丢解锁记录）。
前缀键让每个档案各自独立写，互不影响——与 V1.3 把 `achievementUi` 单独存一个键是同一个理由。

**迁移策略（必须与 V1.3 的 v3 迁移同风格）**
- `version(4)` 的 `upgrade()` 里补 `profileId='default'` 到所有存量行；
- 钩子**永不 rethrow**；失败写 `migration:v4={status:'failed',attempts}`，启动补偿最多 3 次（照抄 v3 的机制）；
- **不合并、不改写** `(packageId, kpId)` 语义，只加一列 —— 这是这一版能安全落地的关键；
- 迁移完成后 UI 里出现"档案切换"，默认档案名"我"。

**硬约束**
- **档案上限 4 个**（D3 裁决：够二胎 + 家长自己体验）。第 5 个的入口直接不出现，
  错误文案是"最多 4 个档案，可以先把不用的档案里的数据导出后再删"。**不做"切换时隐藏"式软上限**——
  隐藏档案等于让数据人间蒸发，比报错难查得多。
- 所有 `recordProgress` / 错题写入 / 成就结算必须带 `profileId`，**没有"全局默认"分支**
  （否则漏改一处就会写进错的档案，且统计层看不出来）。
- 家长端"对比"只显示**并列的两组数字**，不出现"较高/较低""领先/落后"。
- **删除档案是一次显式的高危操作**：必须先导出该档案的备份，再二次确认（输入档案名）。
  删除不回收，且不连带删除其他档案的任何记录。

### P0-3 · 家庭成就墙（含跨设备）

#### P0-3a · 墙的形态（本机）

- 家长端一个页面，按档案各显示一列成就墙（同一组件复用），**无排行、无总分、无冠亚季**。
- 每枚卡只显示"已解锁/未解锁"，**不显示解锁时间先后顺序的对比**（避免变成进度竞赛）。
- 档案超过 2 个时改为**横向滚动分列**，不做"两两对比"布局——`n` 列并排会把屏幕压成火柴盒。
- UI 文案不要出现"家庭组"这种暗示联网的词；用"这台设备上的档案"。

#### P0-3b · 跨设备：载体是备份文件，不是网络（D1 裁决）

**一句话**：跨设备 = 把备份文件搬到另一台设备导入，导入过程**只增不减**。

不做什么（很关键，防止实现跑偏）：无账号、无登录、无上传下载、无 WebSocket、无"设备配对码"。
搬运方式就是家长自己用 U 盘 / 微信文件传输助手 / 网盘挪那个 JSON 文件——对产品来说它就是一个本地文件。

**备份格式 `formatVersion: 2`**

```jsonc
// 现有 exportUserData 产出的是扁平结构（version:'1.0'，progress/mistakes/settings 各一个数组）
// V1.4 新增 v2：按档案分片，同时保留旧字段以便 v1 读取（旧备份读入后整包落到 default 档案）
{
  "formatVersion": 2,
  "exportedAt": "2026-10-20T02:00:00.000Z",
  "activeProfileId": "default",
  "profiles": [
    {
      "profileId": "default",
      "displayName": "我",
      "createdAt": "2026-09-01T00:00:00.000Z",
      "progress":  [ /* 每行带 profileId */ ],
      "mistakes":  [ /* 每行带 profileId */ ],
      "achievements": [ /* UnlockedRecord[]，带 repeatCount */ ],
      "settings":  [ /* 该档案作用域内的键：打卡、每日统计、achievementUi 等 */ ]
    }
  ],
  // 全局（不分档案）的键放这里：customPacks、achievement:audit、主题等
  "globalSettings": [ /* SettingRecord[] */ ]
}
```

**导入 = 三步向导**（对应 U8）

1. **选文件 + 选目标设备上的落点**：列出备份里的每个档案，逐个让家长选
   「并入已有档案（同一孩子的另一台设备）」或「新建档案（另一个孩子）」。
   - 并默认猜测：`displayName` 相同 → 预选"并入"；不同 → 预选"新建"。
   - 新建时若已达 4 个档案上限 → 只能选"并入"，否则不能继续（D3）。
2. **预览（不落库）**：给一张表，每档案一行：`将新增 x 枚成就 / y 条进度 / z 条错题`、
   `将与本机已有记录冲突 w 条（按下面规则取优，不会减少）`、`档案超限 / 无变化` 标记。
3. **执行**：**单个 Dexie 事务内完成**，任一步抛错整笔回滚，并给出"未导入任何数据"的明确结论。

#### P0-3c · 合并规则（"不影响已有进度"的技术定义）

导入前后必须满足**单调不减**：对每个 `(profileId, 指标)`，导入后的数值 `≥` 导入前。
这是 AC-P2-11 的判据，也是这条需求唯一可自动化的表达。

| 数据 | 键 | 冲突时取谁 | 为什么 |
|---|---|---|---|
| 成就解锁 `UnlockedRecord` | `(profileId, achievementId)` | **并集**；`unlockedAt` 取**更早**；`repeatCount` 取**更大**；`evidence` 本机非空则保留、为空才用备份的 | 徽章是事实，两台设备各解锁一次仍是"解锁过"。取更早才是"第一次拿到"的真实时间 |
| 进度 `progress` | `(profileId, packageId, knowledgePointId)` | 比 `lastReviewedAt`，**更晚的整行胜**（**不做字段级合并**） | 字段级合并会造出"进度取自 A、复习次数取自 B"的怪行，`shouldAdvanceSchedule` 会误判 |
| 错题 `mistakes` | `(profileId, exerciseId)` | 比 `lastWrongAt`，**更晚的整行胜**；相等时取 `level` 更高（`mastered > partial > none`）的一行 | 错题等级是"连续答对 2 次"才升级的，取更低等于抹掉孩子的努力 |
| 打卡 / 每日统计 | `(profileId, dateKey)` | 数字字段**逐字段取 max**（题数、时长、正确数） | 这些是累加量，取 max 不会凭空翻倍，也不会因旧备份而变小 |
| 档案列表 `profiles` | `profileId` | 并入时不改 `profileId`；`displayName` 保留本机的 | 改名是家长的显式操作，不该被一次导入悄悄改掉 |
| `achievement:discovery` | `(profileId)` | `lastDrawDay` 取**更晚**；`clues` 取并集 | 取更早会让"今天已经抽过"失效、变成可以刷 | 
| 全局设置 `globalSettings` | `key` | 本机优先（**不覆盖**），仅当本机没有该键才写入 | 主题、包列表这类本机状态被备份覆盖是纯粹的倒退 |

**必须避开的两个既有坑**

- 现有 `importUserData` 在 merge 模式下对 `settings` 是 `db.settings.put(s)`（**整键覆盖**）。
  `achievements` 恰好在 settings 里 → 直接搬过来会抹掉本机成就墙。V1.4 必须按 `(profileId, achievementId)`
  走并集，**不能复用 put 路径**。这是 §1 第 4 条问题的根因，别当成"顺手修一下"。
- 备份是"过去某时刻的快照"，包可能后来被导入/删过。导入前必须 `ensureOwnerIndex()` 重建归属索引
  （V1.3 已踩过：拿错包等于把记录写到别的知识点上），导入后再 `ensureE1Migrated({orphanOnly:true})` 兜一次。

**幂等**：同一份备份连续导入 2 次，第 2 次预览必须显示"无变化"且不写库。否则家长会看到
成就数翻倍、打卡天数暴涨——这是"合并"类功能最容易漏的验收点。

### P1 · 成就导出 / 打印

**分页口径：按小组分页**（D4 裁决）。"小组"就是 `CATEGORY_META` 的四类，顺序固定
`M 精熟目标 → G 成长型思维 → B 行为塑造 → E 探索发现`（与 `CATEGORY_ORDER` 一致）：

| 页 | 小组 | 内置枚数 |
|---|---|---|
| 1 | M 精熟目标 · 🎯 | 8 |
| 2 | G 成长型思维 · 🌱 | 7 |
| 3 | B 行为塑造 · ⏱️ | 8 |
| 4 | E 探索发现 · 🧭 | 5 |

- **每组一页，组内不跨页**。内置 28 枚按 3 列 × 4 行排布，单组最多 8 枚 → 一页装得下，**共 4 页**。
  空组不印空页（自定义包里某组 0 枚时直接跳过，页码连续重编）。
- **自定义包导致的续页**：单组超过一页容量时，组内续页，续页页眉标「M 精熟目标（续）」，
  页脚用 `第 x / n 页` 连续计数，**不重编**。续页只会在启用自定义包后出现。
- 页眉：档案显示名 + 小组名 + 该组「已获得 x / y」；页脚：导出日期 + 页码。
  **不印"完成率 %"** —— 百分比会立刻变成家长之间的比较工具。
- 导出图片与打印**共用同一套分页**：`achievements-M.png` / `-G.png` / `-B.png` / `-E.png` 四张，
  不再出"一页 28 枚"的大图（两套排版就是两套不一致的种子）。
- **黑白也能看出层级**：星标数量 + 边框粗细 + 层级文字（家长版显示 `TIER_META.label`），
  颜色不是唯一编码（AC-P2-10）。
- 打印样式单独一份 CSS，走**固定浅色 token**，不继承暗色主题。
- 不含真实姓名以外的隐私信息；文件名用档案显示名（可改），不用真名。

### P2 · 重复纪念印记 / 故事卡

- 已解锁的成就再次达成 → 记一次 `repeatCount`，卡片右下角显示"第 2 次"小印记（`aria-label` 同步）。
- **不额外给奖励、不加分、不改变层级** —— 只记录事实。
- 故事卡：把"解锁时间 + 证据 + 关联学习记录"拼成一张可保存的卡片（仍需 token 化样式）。

## 5. 数据与兼容

- 新增 settings 键：`achievement:customPacks`（启用列表 + 版本快照，**全局**）、
  `achievement:audit`（**全局**）、`profiles`（档案列表 + 当前档案，**全局**）。
- 现有键 `achievements` / `achievementUi` / `achievement:collectionSeen` / `achievement:discovery`
  **全部按档案分片为前缀键**（见 §P0-2 的选择理由），`upgrade()` 里逐键搬到
  `default` 档案下，**一条都不能丢**（漏一个的表现是"某个孩子的打卡天数突然归零"）。
- 四个高频键的分片对照：

  | 原键 | V1.4 形态 | 备注 |
  |---|---|---|
  | `achievements` | `achievements:<profileId>` | `UnlockedRecord[]`，含 `repeatCount` |
  | `achievementUi` | `achievementUi:<profileId>` | 折叠状态是"这个孩子的界面"，必须分片 |
  | `achievement:collectionSeen` | `achievement:collectionSeen:<profileId>` | 不分片会让老二看不到自己的全收集卡 |
  | `achievement:discovery` | `achievement:discovery:<profileId>` | 不分片会两个孩子共用"今天抽过" |

- **跨设备兼容矩阵**（D1 的直接后果）：

  | 备份来源 | 目标设备 | 结果 |
  |---|---|---|
  | v1.0 扁平备份 | V1.4 | **允许**，整包落到 `default` 档案，按 §P0-3c 规则合并 |
  | v2（`profiles[]`） | V1.4 | **允许**，走导入向导 + 档案映射 |
  | v2 | V1.3 | **拒绝**，明确报错"备份来自更高版本，请先升级"。不做降级兼容（旧代码不认识分片键，会静默丢数据） |

- 备份里的**包内容不在 V1.4 范围内**：跨设备搬成就时若目标设备没装对应学习包，进度行会变成"孤儿行"。
  导入后照 V1.3 的做法跑 `ensureE1Migrated({orphanOnly:true})` 尝试归因；仍归不了的**保留不删**
  （等家长装了包自然就归上了）。

## 6. 验收标准（二元可判定）

| # | 验收项 | 判定 |
|---|---|---|
| AC-P2-1 | 导入一个 `id` 与内置成就冲突的包 | 拒绝并提示具体冲突 id，库内零变化 |
| AC-P2-2 | 包内 `rule.kind` 不在白名单 | 校验失败，不进入预览（`expr` / `script` / `js` 等未知 kind 全部命中此条） |
| AC-P2-3 | 启用自定义包后停用 | 自定义卡从视图消失，`UnlockedRecord` 仍在；重新启用后卡与解锁态都回来 |
| AC-P2-4 | 回滚到上一版包 | 视图回到上一版，解锁记录一条不少 |
| AC-P2-5 | 从 V1.3 库升级到 V1.4 | 所有存量行 `profileId='default'`，行数不变，统计数字前后一致（逐项对比） |
| AC-P2-6 | v4 迁移失败（注入 IO 错） | 启动不崩、写 `migration:v4 failed`、下次启动重试，上限 3 次 |
| AC-P2-7 | 档案 A 答题 | 档案 B 的进度/错题/成就/打卡数字**一个都不变** |
| AC-P2-8 | 家庭成就墙 | 页面文本里不出现"排名/第 1 名/领先/超过"等词（静态断言 + 人工复核） |
| AC-P2-9 | 同机导出后重新导入 | 28 枚内置 + 自定义包的解锁记录完全一致（含 `evidence`），且导入后总数不变 |
| AC-P2-10 | 打印页灰度截图 | 三档层级在去色后仍可区分（星标数量 + 边框粗细不同） |
| **AC-P2-11** | **跨设备往返**：A 机导出 → B 机导入（B 机已有自己的记录） | 对每个 `(profileId, 指标)`，**导入后 ≥ 导入前**；`已获得枚数` 只增不减；`evidence` 非空项一条不丢 |
| **AC-P2-12** | **旧备份不倒退**：B 机上某 kp 的 `lastReviewedAt` 比备份里晚 | 该行**保持本机版本**；导入后掌握率不变（不出现"越导越差"） |
| **AC-P2-13** | **幂等**：同一份备份连续导入 2 次 | 第 2 次预览显示"无变化"且**不写库**；成就数、打卡天数不翻倍 |
| **AC-P2-14** | **档案上限**：已有 4 个档案时导入含"新建"选择的备份 | 新建选项不可选，只能并入；库内档案数仍为 4 |
| **AC-P2-15** | **导入原子性**：执行阶段注入一次写失败 | 整笔回滚，库内零变化，提示"未导入任何数据"（不出现"导入了一半"） |
| **AC-P2-16** | **打印分页**：内置 28 枚 + 某组 3 枚自定义包 | 每页只含一个小组；M/G/B/E 顺序正确；空组不出页；页码连续；单组超容量时续页标"（续）"且页码不重编 |
| **AC-P2-17** | **settings 整键覆盖回归**：拿一份 V1.3 旧备份（`settings` 里含旧 `achievements` 键）导入 | 本机成就墙**不被抹掉**；`achievements:<pid>` 走并集而非 `put` 覆盖（守 §1 第 4 条根因） |

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| `profileId` 漏改一处 | 数据写进错档案，且**统计层看不出来**（数字都对，只是归属错） | 写入端收口（照 V1.3 的 `recordProgress` 归一化思路）：所有写入走单一函数，调用点拿不到"无 profile"分支；迁移前后做行数与逐项数字比对 |
| **合并写成字段级** | 造出"进度取自 A、复习次数取自 B"的怪行，`shouldAdvanceSchedule` 误判 → 复习排期乱 | 进度/错题**整行胜**（比 `lastReviewedAt` / `lastWrongAt`），只有累加量（打卡、每日统计）才逐字段 max。写进 §P0-3c 表并单测锁死 |
| **旧备份覆盖新进度** | 导入一次掌握率反而下降，家长会认为"这软件把我的数据搞坏了" | AC-P2-12 + **单调不减**作为唯一判据；实现上禁止"备份优先"的单向覆盖 |
| 重复导入导致翻倍 | 成就数、打卡天数虚高，且不可逆 | AC-P2-13 幂等：第 2 次预览必须"无变化"且不写库 |
| 导入中途失败 | 半截数据比不导更难查 | 单事务执行，失败整笔回滚（AC-P2-15） |
| 两台设备版本不一致 | V1.3 读 v2 备份会静默丢分片键 | §5 兼容矩阵：低版本读高版本备份**直接拒绝**，不尝试兼容 |
| **Tauri 下导出的文件家长找不到** | "跨设备"这条需求直接从第一步断掉 | 导出后用系统对话框"另存为"并**显示完整落盘路径**；Web 版沿用下载目录并给出提示文案 |
| 自定义包质量不可控 | 刷屏式成就、误导性文案 | 单包上限 20 枚；文案长度上限；预览必须显示"新增/冲突"；不提供 `script` 类规则 |
| 家庭墙变成攀比 | 违背产品伦理 | 不做排行/总分；文案不含比较级（写进 AC-P2-8）；打印不印完成率 |
| 打印样式破坏主题 | 白底打印出深色块 | 打印样式单独一份 CSS，走固定浅色 token，不继承暗色主题 |
| 4 个档案上限撞上导入 | 家长搬进来第 5 个孩子时被卡住 | 超限时只允许"并入"，文案引导"先导出再删"；不做静默丢弃 |

### 8.1 裁决 1 留下的一个新问题（进架构时必须回答）

**两台设备的 `default` 档案，是"同一个孩子"还是"两个不同孩子"？** 产品无法自动判断，只能问家长。
P0-3b 的向导把这个问题显式化（并入 / 新建），并给"同名预选并入"的默认值。
但架构上要定一件事：**导入时 `profileId` 是否允许重写**（把备份里的 `default` 映射成本机的 `p2`）。
建议允许 —— 否则"两个不同孩子恰好都叫 default"时只能丢弃数据。这条**不是产品决策，是数据模型决策**，
留给架构设计回答。
