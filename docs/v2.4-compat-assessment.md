## 1.2 数据断层风险（虚拟 Good 喂 FSRS）

**结论：不会引发数据震荡，但有"掌握态与排期不一致"与"诚信漂移"两类风险。**

- 能进复习清单的 KP 必有 `progress` 行（首次学习即建行），故不存在"从未做过题却混进清单"的 KP。对一个已学卡片喂 `Good`：`scheduler.next()` 走 FSRS 成功分支，`stability` 抬升、`due` 前移、`reps+=1`——**确定性单次转移，无算法层面损坏**。
- 上界受 `fsrs.ts` `MAX_INTERVAL_DAYS = 365` 封顶（`fsrs.ts:50` 区域），`due` 最多推到 365 天后，不会无限跳跃。
- **风险 A（必须复用门控）**：若按钮不套 `shouldAdvanceSchedule`（`:201`），重复点击会反复调 `scheduleReview` 把 `due` 越推越远。
- **风险 B（掌握态滞后）**：虚拟 Good 只写 `fsrs/nextReviewAt/lastReviewAt`，**绕过 `recordProgress` 的 `status/correctCount/bkt/masteryProbability`（`:259-320`）**。因复习清单只看 `nextReviewAt`（`:200`），对"今日是否出现"无影响，但家长页/报告的 `status` 统计会短暂滞后。
- **风险 C（产品诚信）**：FSRS 会"误以为"已掌握，排期逐步推乐观。因 `shouldAdvanceSchedule` 同天只推进一次，不会同日内反复推远，属可接受漂移。

## 1.3 成就联动风险

**结论：无破坏风险。** 28 枚成就无一枚读取复习次数 / `fsrs` / `nextReviewAt`（`achievements.ts` 全表 + `achievement.ts` `buildContext` 已证）。虚拟 Good 不调 `touchStudyDay`（不影响 streak）、不改 `correctCount`（不影响 M/G 类）、不改 `mistakes.reviewCorrectCount`（不影响 `review-20`）。即：**点"已复习"不真学，既不会误解锁任何成就，也不会贡献任何成就进度——符合"成就反映真实学习"的预期。**

## 1.4 三方案可行性打分

### 方案 A（纯手动「✅ 已复习」+ 虚拟 Good）
- **可行性：高（实现）/ 中（产品）**
- 实现：在 `Review.vue` 加按钮 → `scheduleReview({ card: row.fsrs, rating: Rating.Good })` → 写回既有 `progress` 行的 `fsrs/nextReviewAt/lastReviewAt`（复用 `recordProgress` 落库形态，但**必须套 `shouldAdvanceSchedule` 门控**）。
- 风险：① 不复用 `:201` 门控 → `due` 被反复推远；② `status/bkt` 滞后（风险 B）；③ 诚信漂移（风险 C）。
- 对成就：无影响（见 1.3）。

### 方案 B（复习入口跳转到 Mistakes.vue 按 KP 筛选）
- **可行性：中**
- 数据结构可行：`MistakeRecord.knowledgePointIds: string[]`（`src/db/index.ts` 区域）支持按 kpId 筛。
- 缺口：`Mistakes.vue` **无单 KP 筛选/深链能力**（`:480` 仅分组），需新增 `?kp=<id>` 过滤入口。
- **硬伤**：对"无错题"的 KP 无 fallback（需求明确要按钮）→ **单独方案 B 无法满足需求**，必须配 A（即落到 C）。

### 方案 C（双管齐下：默认只做错题，做完即完成；无错题才展示按钮）
- **可行性：中高（最贴合需求，但有一处必补联动）**
- "做完错题即完成"依赖错题经题目流 `recordProgress` 推进 `nextReviewAt`（`TopicDetail.vue`/`ExamPanel.vue` 已落实"重做错题 → `recordProgress` + `resolveMistake` 联动）。
- **关键风险（最易踩）**：若把"完成"误判为在 `Mistakes.vue` 点「我已掌握」，`markAsMastered`（`:164`）**不推进 `progress.fsrs`**，KP 仍会因 `nextReviewAt` 到期留在清单，"完成"判定失效。必须让错题经**题目流** `recordProgress` 才算完成，或把"标记 mastered"信号显式回灌 `recordProgress`。
- "无错题才展示按钮"：需先判定该 KP 是否仍有 `pendingMistakes`（`needsReview`，`src/core/mistake/mistakeRules.ts:81`），可在复习清单项叠加（Review.vue 已能拿到 `kpId`，可 join `userDataStore.mistakes`）。

## 1.5 降级方案（推荐）

**推荐方案 C**，并把"无错题时的按钮"实现为方案 A 的受控虚拟 Good：
1. 进入复习 → 若 KP 有 `pendingMistakes` → 跳 `Mistakes.vue?kp=<id>`（补 B 的筛选入口），做完经题目流 `recordProgress` 自然出清单；
2. 若 KP 无错题 → 展示「✅ 已复习」，点击 = `scheduleReview(Good)` + **套 `shouldAdvanceSchedule` 门控** + 写回 `fsrs/nextReviewAt/lastReviewAt`，**不**改 `status/bkt`；
3. **严禁**把"Mistakes.vue 标记 mastered"当作复习完成信号（除非回灌 progress）。

若工期极度紧张，可先交付**纯方案 A**（风险 B/C 可接受，成就无影响），方案 B 的筛选入口留待后续。

# 任务 2 · 语文词汇「分单元」兼容性评估

## 2.1 数据结构现状（⚠️ 前提偏差，请先确认）

> **实测结论与需求描述不符**：磁盘上词汇包 `content/chinese-4-up-rjb/special-chinese-4-up-vocab.json` **只有 3 个单元**（`vocab-u1/u2/u3`，标题"词语表 1/2/3"，共 220 词：81+90+49），**且每个单元已是 1 个 topic**（`vocab-t1/t2/t3`）。你提到的"7 个单元混在一起"疑为把教材的 `unit-chinese-4-up-rjb-u1..u8`（8 个单元包）记混。**无论单元数多少，本包 `units[]` 已显式带逐单元 KP 列表这一结构事实不变，结论同样适用。**

| 事实 | 位置 | 说明 |
|---|---|---|
| 词扁平数组、词本身无 `unitId` | 包 JSON `knowledgePoints[]`（行 16-238） | 每条 `{id:"cn-vocab-001", type:"word", ...}`，无 unit 段 |
| 单元显式分组 | 包 JSON `units[]`（行 241/299/359） | `vocab-u1.topic.vocab-t1.modules[0].knowledgePointIds` = `cn-vocab-001..081`，逐单元列全 |
| 分组 key 可用 | `resolvePackageUnits.ts:95` `findUnitByKnowledgePoint` | 给定任一词可定位其 unit（已实现，可复用） |
| 进度粒度到"词" | `userData.ts:234` 复合索引 | `(profileId, packageId, knowledgePointId)`，**无 unit 列** |
| 词级进度天然蕴含单元进度 | `cardStatus.ts:298` `unitCardStatusOf` + `:273` `collectKpIds` | **UnitList 每单元卡已显示独立掌握状态**（派生，不改库） |
| 总进度按整个包 | `masterySummary.ts:99/170/108` | `computeMasterySummary` 遍历 `pkg.knowledgePoints` 算全包掌握率 |
| VocabDrill 扁平无 unit | `src/modules/core/VocabDrill.vue:168` `props.words`；`:273` `recordProgress(props.packageId, word.id, ...)` | 纯词数组 prop，自身不查包 JSON，无 unit 概念 |
| 词如何进 VocabDrill | `src/modules/chinese/ChineseWords.vue:10` 调 `<VocabDrill>`；`:41/46` 传 `knowledgePointIds` | 由当前 topic 的 module 提供——**对词汇包即"该单元的词"**，故"点进某单元 topic 已只背该单元词" |

**现状关键发现**：词汇包的"分单元"在**数据结构与导航链路（UnitList→TopicList→TopicDetail）上已经成立**。用户当前若从单元列表点进去，背的其实就是那个单元的词。需求痛点更可能是"VocabDrill 内部无法在单元间切换"或"希望一个页面内选单元"，而非"数据混在一起"。

## 2.2 进度追踪断点

- **无需重构 `recordProgress` / `knowledgePointId`**：进度粒度到"词"，单元进度是 `unitCardStatusOf`（`:298`）查出来的派生视图，不是单独存一份。
- 若强行"彻底拆分"（让同一词在不同单元独立计分）：词在各单元**互不重叠**（1-81/82-171/172-220），此优势当前不成立，且要重构 `userData.ts:234` 复合索引 + `ownerIndex.ts` 归一化 + `masterySummary.ts` 全族（`:57/99/144/278`）+ 所有消费方（TopicDetail/复习/弱项/成就）——牵一发动全身。

## 2.3 UI 接入方式

- **方式一（推荐，不改路由）**：在 `ChineseWords.vue` 顶部加「单元下拉框」，把全包 `units` 传入后按 `unit.id` 过滤 `knowledgePointIds` 再 `:words`。改动集中在 `ChineseWords.vue`（约 +1 `<select>` + 1 过滤 computed）。
- **方式二（独立单元选择页）**：现有 `router/index.ts` 的 `/learn/:packageId/unit/:unitId` → `TopicList` → `TopicDetail` 链路**已存在**，无需新增页。

## 2.4 方案甲（彻底拆分）vs 方案乙（前端分页）优劣势

| 维度 | 方案甲（彻底拆分 / 重构 knowledgePointId） | 方案乙（前端分页 / 按 unit 过滤） |
|---|---|---|
| 内容包改动 | 需改 JSON 层级 + 同步 `schemas/knowledge-point.ts` 与 `normalizePackage` 校验 | **零改动**（units[] 已显式带 KP） |
| 数据库 / 索引 | 改 `userData.ts:234` 复合索引加 unit 维度 | 不改 |
| 聚合消费者回归 | `masterySummary` 全族 + TopicDetail + 复习 + 弱项 + 成就 全部回归 | 无 |
| 内容校验 | W021-W023 不扫词汇挂载层级（已证），但结构变更有隐性成本 | 不触发任何校验 |
| 当前收益 | 仅当"同词跨单元独立计分"才有意义——本包词不重叠，**收益不成立** | 直接满足"点哪单元背哪单元" |
| 风险评估 | **高代价、低收益，不推荐** | **低风险，推荐** |

## 2.5 降级方案（推荐）

**直接采用方案乙**：
1. `ChineseWords.vue` 接收全包 `units`，顶部加单元下拉框，按 `units[].topics[].knowledgePointIds` 过滤后传 `:words`；
2. 若产品强调"drilling 时看本单元进度"，在 `VocabDrill` 内加一个**派生**小进度条（由传入该单元词集合 + 现有 `progressOf` 逻辑，仍不改库）；
3. UnitList 单元卡已显示独立掌握状态（`:298`），无需额外工作。
**方案甲仅在确认"需求是同词跨单元独立计分"时才考虑；否则属过度重构。**

1. **任务 1**：推荐方案 C（做完错题 + 无错题受控虚拟 Good），**不破坏 FSRS 排期（无震荡）、不影响成就体系**。红线：R1、R3。

   - 词汇"7 单元"的真实来源（实测为 3 单元，疑与 8 个教材单元包混淆）；
   - 是否需要"drilling 内单元进度条"（决定方案乙是否加派生进度）；
   - 复习"✅ 已复习"是否接受"掌握态统计短暂滞后"（R2）。
